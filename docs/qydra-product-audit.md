# تدقيق CONSEDRA Finance OS وتحويله إلى QYDRA OS

## الخلاصة التنفيذية

المنصة الحالية ليست مشروعاً جديداً يحتاج إلى إعادة بناء؛ بل تحتوي بالفعل على نواة قوية لنظام مالي سعودي متعدد الشركات، تشمل المحاسبة مزدوجة القيد، المبيعات وCRM، الفوترة، بوابة العميل، الصلاحيات، سجل التدقيق، الإقفال المالي، التقارير، هوية الشركة، والتشغيل على VPS. لذلك يعتمد المسار الآمن على **التطوير التدريجي** مع الحفاظ على اسم CONSEDRA والهوية الحالية إلى أن يقرر المالك اعتماد QYDRA كاسم منتج تجاري.

> قاعدة التنفيذ: لا نضيف عشرات الوحدات دفعة واحدة؛ نغلق فجوات الجاهزية التجارية والأمان والامتثال أولاً، ثم ننتقل إلى المزايا التنافسية.

## خريطة الحالة الحالية

| المجال | الحالة الحالية | الفجوة أو المخاطر | الأولوية | القرار |
|---|---|---|---|---|
| Multi-Tenant | موجود ومستخدم في الاستعلامات والعلاقات | يحتاج اختبار ضغط وعقود عزل آلية أوسع | P0 | الحفاظ والتوسعة بالاختبارات |
| المحاسبة مزدوجة القيد | موجودة مع دليل حسابات وتقارير وإقفال | يلزم استكمال سيناريوهات التسويات والأرصدة الافتتاحية والعملات المتعددة | P0 | تدقيق تكاملي قبل التوسع |
| RBAC | أدوار تفصيلية وعزل للمبيعات والفوترة ومساعد الرئيس التنفيذي | الصلاحيات المخصصة وواجهة بناء الأدوار غير مكتملة | P0/P1 | إضافة Custom Roles تدريجياً |
| Audit Trail | سجل تدقيق غير قابل للحذف ومسارات مراجعة | يلزم توحيد IP والجهاز والقيم السابقة/اللاحقة في كل المسارات | P0 | توحيد الحد الأدنى للتدقيق |
| ZATCA | QR وقوالب وطبقة تكامل وحالات جاهزية | لا يُعلن اعتماد رسمي قبل ربط الشهادات وبيئة الاختبار والإرسال الفعلي | P0 | إبقاء التكامل قابلاً للتفعيل بعد الاعتماد الرسمي |
| المبيعات والفوترة | مفصولة، مع CRM وعروض أسعار وفواتير وتحويل وتحصيل | دورة Sales Order والدفعات الجزئية والاشتراكات غير مكتملة | P1 | تنفيذ الفجوات ذات القيمة التشغيلية أولاً |
| بوابة العميل | مشاهدة المستندات وقبول/رفض العروض | الدفع الإلكتروني والتوقيع ورفع المستندات تحتاج مراحل لاحقة | P1/P2 | الحفاظ على البوابة الحالية وتوسيعها بأمان |
| AI CFO | مساعد مالي موجود بمصادر بيانات النظام | يحتاج عقود إجابة قابلة للتتبع ومنع الأرقام غير المصدرية واختبارات تقييم | P1 | بناء طبقة تفسير ومصادر قبل التنبؤ |
| الهوية والتخصيص | هوية شركة مع شعار وألوان ورفع مباشر وعزل | يلزم تطبيقها على PDF والقوالب الرسمية | P1 | ربط الهوية بالمخرجات الرسمية |
| Smart Onboarding | إعداد شركة وفترات وفريق موجود | لا يزال مساراً داخلياً أكثر من كونه اشتراكاً تجارياً ذاتياً | P0/P1 | تحويله إلى خطوات واضحة مع حالات اكتمال |
| الاشتراكات | غير مكتمل كمنتج SaaS مدفوع | لا توجد باقات واستحقاقات وحدود استخدام ودفع تجاري كامل | P0 | بناء نموذج اشتراك أولي قبل أي توسع تجاري |
| المراقبة | سجلات تشغيل وفحوصات نشر ونسخ احتياطي | يلزم مركز صحة وقياس استخدام ومنبهات تشغيل | P1 | إضافة مؤشرات داخلية دون كشف بيانات العملاء |

## نطاق الإطلاق التجاري الأول

يجب أن يركز الإصدار الأول القابل للبيع على التسجيل أو الدعوة، إنشاء الشركة، إعداد الملف النظامي، إضافة الفريق، ضبط الأدوار، العملاء، عروض الأسعار، الفواتير، تسجيل المدفوعات، المصروفات، المحاسبة، التقارير، بوابة العميل، والهوية المخصصة. أما التنبؤ المتقدم، التجميع بين الشركات، إصدار المكاتب المحاسبية، التكاملات البنكية، WhatsApp، وSSO فتُصنف توسعات لاحقة ولا ينبغي أن تؤخر الإطلاق الآمن.

## قرارات معمارية

سيُحافظ على React وTypeScript وtRPC وDrizzle وMariaDB وDocker Compose مع استمرار العزل عبر tenantId وcompanyId. ستُضاف طبقة استحقاقات مستقلة عن اسم الباقة، بحيث يمكن تفعيل وحدة أو حد استخدام لكل شركة دون تعديل منطق كل شاشة. وستظل الحسابات المالية داخل محرك الحسابات، بينما يفسر الذكاء الاصطناعي الأرقام ويعرض مصدرها ولا ينفذ عمليات حساسة دون موافقة وصلاحية.

## ترتيب التنفيذ

| المرحلة | النطاق | معيار الإنجاز |
|---|---|---|
| P0-A | الاشتراكات والباقات والاستحقاقات وحالات التجربة | إنشاء شركة، خطة، حدود، حالة اشتراك، ومنع استخدام وحدة غير مستحقة |
| P0-B | Smart Onboarding تجاري | خطوات واضحة مع حفظ التقدم وحالة جاهزية الشركة |
| P0-C | تدقيق الأمن والامتثال والمحاسبة | اختبارات عزل وصلاحيات وتدقيق وإصدار تمنع المسارات الخطرة |
| P1-A | AI CFO قابل للتتبع | كل رقم مرتبط بمصدر وفترة، مع حالات عدم كفاية البيانات |
| P1-B | تخصيص المستندات والهوية | الشعار والألوان والاسم تظهر في PDF والقوالب الرسمية |
| P1-C | تحسين التحصيل وبوابة العميل | دفعات جزئية، كشف حساب، تذكير، ورفع مستندات وفق صلاحيات |
| P2 | التنبؤ ولوحة القرار والتكاملات | مخرجات تحليلية مبنية على بيانات كافية وبمراجعة بشرية |
| P3 | المكاتب المحاسبية والتجميع وEnterprise | Multi-Entity وSSO وAPI ومركز إدارة منصة منفصل |

## عناصر يجب الحفاظ عليها

يجب عدم كسر فصل قسم المبيعات عن الفوترة، عزل ممثل المبيعات، صلاحيات مهند الرقابية، بوابة قبول/رفض عروض الأسعار، الترقيم التلقائي، التاريخين الميلادي والهجري، الباركود الضريبي، حماية القيود المرحلة، سجل التدقيق، الإقفال المالي، وإعدادات الهوية متعددة الشركات.

## ملاحظات الإطلاق

لا يجوز وصف النظام بأنه معتمد من ZATCA أو أنه يرسل فواتير إنتاجية قبل اكتمال الشهادات وبيئة الربط والاختبار الرسميين. كما يجب ألا تُفعّل المدفوعات أو الاشتراكات التجارية قبل وجود سياسة استرداد وبيانات فوترة واختبارات فشل الدفع. تغيير الاسم إلى QYDRA OS قرار منتج وهوية تجارية، ولذلك يُنفذ بعد تأكيد المالك، وليس كاستبدال مفاجئ لهوية CONSEDRA الحالية.
